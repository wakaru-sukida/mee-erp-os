Global Master + Tenant Override — แนวทางที่เลือก

Master กลาง (geo/currency) ไม่มี tenant_id · ปรับแต่งรายผู้เช่าผ่าน override table · อ่านแบบ union · Mee-ERP OS

ข้อสรุป: แยกข้อมูลเป็น 2 ชั้น — Global master เก็บชุดเดียวใช้ร่วมทุกผู้เช่า (ไม่มี tenant_id), ส่วนการปรับแต่งเฉพาะผู้เช่าไปอยู่ในตาราง override ที่มี tenant_id เวลาอ่าน = global ∪ override ของ tenant นั้น

ชั้นที่ 1 · GLOBAL

Global Master

country · province · district · subdistrict · currency

ไม่มีคอลัมน์ tenant_id — เก็บชุดเดียว, single source of truth, แก้ที่เดียวเห็นทุกผู้เช่า

ชั้นที่ 2 · PER-TENANT

Override Tables

tenant_geo_override · tenant_currency_override

tenant_id NOT NULL + RLS + status — เพิ่มเขต/พื้นที่/สกุลเงินเฉพาะองค์กร โดยไม่แตะตารางกลาง

ทำไมไม่ใส่ tenant_id ลง master กลาง

  • ถ้าใส่ = ทุกผู้เช่าต้องมีสำเนา 77 จังหวัด / 928 อำเภอ / 7,436 ตำบล ของตัวเอง → ข้อมูลบวม (7,436 × จำนวน tenant) และซ้ำซ้อน
  • อัปเดตข้อมูลกลาง (เพิ่มตำบล/แก้ชื่อ) ต้องไล่แก้ทุก tenant แทนที่จะแก้ที่เดียว
  • ขัดหลัก single-source-of-truth ที่วางไว้

กติกาการอ่าน (Resolve)

  • อ่าน = global master ∪ override ของ tenant นั้น
  • ถ้า override มี key ชนกับ global (เช่น แก้ชื่อจังหวัดเดิม) → override ชนะ เฉพาะ tenant นั้น
  • id ของ override ต้องไม่ชน global — ใช้ prefix/namespace หรือ UUID
  • FK จากตาราง tenant-owned (เช่น branch.province_id) ต้อง resolve ได้ทั้งจาก global และ override
-- ตัวอย่างการอ่านจังหวัดของ tenant 42
SELECT province_id, province_name FROM province          -- global
UNION ALL
SELECT province_id, province_name FROM tenant_geo_override
  WHERE tenant_id = 42 AND kind = 'province' AND status = 'active';

สรุป tenant_id ต่อตาราง

กลุ่มตารางtenant_idหมายเหตุ
tenant-owned
branch · department · transaction ฯลฯ		NOT NULLทุกแถวต้องรู้เจ้าของ + RLS
override
tenant_geo_override · tenant_currency_override		NOT NULLปรับแต่งรายผู้เช่า + RLS
global master
geo · currency		ไม่มีคอลัมน์ใช้ร่วมทุกผู้เช่า

ตอน Export → Siloed

  • copy global master ทั้งชุด + override ของ tenant นั้น ไปตั้งต้น DB ใหม่
  • merge เป็น master ชุดเดียวใน DB ใหม่ได้เลย (หรือคง 2 ชั้นไว้ก็ได้)
  • ป้องกัน FK หัก: master ต้องตามไปพร้อม tenant data เสมอ

หมายเหตุ: โมเดล “tenant_id nullable = global” (เก็บ global กับ tenant data ปนตารางเดียวแล้วใช้ NULL แทน global) ไม่ใช้แล้ว เมื่อเลือกแยกตาราง — global master จึงไม่มีคอลัมน์ tenant_id เลย ทำให้ RLS เขียนตรงไปตรงมา ไม่ต้องเผื่อเงื่อนไข NULL
