RLS ต้องมี tenant_id ทุกตารางไหม?

ความเข้าใจผิดที่พบบ่อย — RLS กับ Composite FK ต่างกันที่ “ใช้ tenant_id ทำอะไร” ไม่ใช่ “มี tenant_id หรือไม่” · Mee-ERP OS

ข้อสรุป: RLS ก็ต้องมี tenant_id ในทุกตาราง tenant-owned เหมือน Composite FK — ไม่ใช่ใส่แค่ตาราง company ตารางเดียว

ทำไม RLS ต้องมี tenant_id ในตารางนั้นเอง

ดูที่ตัว policy — tenant_id ในเงื่อนไขคือ คอลัมน์ของตาราง branch เอง ถ้า branch ไม่มีคอลัมน์นี้ policy จะเขียนไม่ได้เลย:

ALTER TABLE branch ENABLE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation ON branch
  USING (tenant_id = current_setting('app.tenant_id')::bigint);
  -- ↑ tenant_id ตัวนี้ = คอลัมน์ของ branch

RLS ทำงานโดย “อ่านค่า tenant_id ของแต่ละแถว” มาเทียบกับ tenant ปัจจุบัน ดังนั้นทุกตารางที่จะกันข้าม tenant ต้องเก็บ tenant_id ของตัวเอง

แล้วแบบ “tenant_id เฉพาะ company” ล่ะ?

แบบที่เก็บ tenant_id ไว้แค่ตาราง company แล้วให้ตารางลูก join กลับไปหา มีจริง เรียกว่า resolve ผ่าน parent — แต่ policy จะกลายเป็น subquery ที่ต้อง join ทุกครั้ง:

CREATE POLICY tenant_isolation ON branch USING (
  EXISTS (SELECT 1 FROM company c
    WHERE c.company_id = branch.company_id
      AND c.tenant_id = current_setting('app.tenant_id')::bigint)
);

ข้อเสีย: ทุก query ต้อง join → ช้า, เขียน policy ยุ่ง, และพลาดง่ายกว่า

เพราะเหตุนี้ระบบ Pooled จริงจึง denormalize tenant_id ลงทุกตาราง tenant-owned — ทั้ง RLS และ composite FK ทำงานได้เร็วและเขียนง่ายกว่า ไม่ต้อง join ย้อนไปหา company ทุกครั้ง ส่วน Master กลาง (ประเทศ/จังหวัด/อำเภอ/ตำบล, สกุลเงิน) ยังคงเป็น platform-global ไม่มี tenant_id ตามเดิม
