การกันข้อมูลข้าม Tenant (Cross-Tenant Isolation)

Composite FK / CHECK และ Row-Level Security — สำหรับโมเดล Pooled Multi-Tenant · Mee-ERP OS

เป้าหมาย: ผู้เช่า A ต้อง ไม่ สามารถอ้าง เห็น หรือแก้ข้อมูลของผู้เช่า B ได้ — แม้โค้ดจะมี bug หรือลืมกรอง โดยบังคับที่ชั้นฐานข้อมูล ไม่พึ่งวินัยของโปรแกรมเมอร์อย่างเดียว

1Composite FK — กันที่ระดับความสัมพันธ์ (Integrity)

FK ปกติเช็คแค่ว่าค่าปลายทาง “มีอยู่จริง” แต่ไม่เช็คว่าอยู่ tenant เดียวกัน → เผลอผูก branch ของ A ไปหา company ของ B ได้ วิธีกันคือใส่ tenant_id ในทุกตาราง แล้วทำ FK เป็น คู่ ให้ tenant ต้องตรงกันด้วย

-- company: unique (tenant_id, company_id)
-- branch อ้างอิงแบบคู่ (composite):
FOREIGN KEY (tenant_id, company_id)
  REFERENCES company (tenant_id, company_id)

ผล: ฐานข้อมูลปฏิเสธทันทีถ้า branch.tenant_id ≠ company.tenant_id — ผูกข้าม tenant ไม่ได้ตั้งแต่โครงสร้าง

CHECK = ทางเลือกที่เบากว่า บังคับเงื่อนไขภายในแถวเดียว (เช่นค่าห้ามขัดกัน) แต่เช็คข้ามตารางตรงๆ ไม่ได้ — เคสข้ามตารางจึงใช้ composite FK หรือ trigger แทน

2Row-Level Security (RLS) — กันที่ระดับการเข้าถึง (Access)

ฟีเจอร์ของ DB (เช่น PostgreSQL) ที่ กรองแถวอัตโนมัติทุก query ตาม tenant ปัจจุบัน โดยแอปไม่ต้องเขียน WHERE tenant_id=… เอง

ALTER TABLE branch ENABLE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation ON branch
  USING (tenant_id = current_setting('app.tenant_id')::bigint);

แอปตั้งค่า tenant ตอนเปิด connection (SET app.tenant_id = 42) จากนั้น SELECT * FROM branch จะเห็นเฉพาะแถวของ tenant 42 — แม้ลืมกรอง ก็รั่วไม่ได้
